# 知识图谱版本治理

## 当前约定

项目只向使用者提供两个完整图谱数据分支：

- v1直接全库抽取：历史原始基线，数据版本1.0.0。
- v2实体完善工作版：当前持续完善分支，登记快照2.0.0-dev.20261021，下一步完善关系和条件。

schema保持4.0.0-draft；数据分支名称与相邻“旧版本”目录中的旧schema不是同一概念。入口以项目根目录CURRENT.json为准，清单在versions/index.json。README与MASTER提供人类导航。

## 产物、来源与状态

每个版本目录包含一份独立、完整、可直接读取的图谱，以及SHA-256、大小、数量、来源文件指纹和状态清单。v1原始结果不是已审核图谱；v2仍有pending/unresolved。登记的文件内容固定，后续修正必须另存新快照，不能在同一版本ID下静默覆盖。

继承关系：直接全库抽取 → 保守筛选中间结果 → 实体完善及整合。v2比v1少的事实来自中间筛选，不是实体整合删除事实。筛选图、实体增量、模型响应和失败记录仍在原reports位置；保留旧路径是为了保护来源引用、缓存和复现命令。本轮没有移动、删除或重写这些数据文件。

## Git与大文件

Git管理当前代码、测试、schema/registry、文档、版本清单和哈希；本地大型图谱JSON及运行证据目录由.gitignore排除。既有已跟踪文件不因新增ignore规则自动移除。

本次建立本地代码/治理检查点，不远程推送。它记录当前工程状态，不能追认原始抽取时的代码提交；历史生产提交不确定时manifest保留null。各阶段报告的测试数量只代表对应阶段，不直接累加。

**Git记录不能代替数据备份。** 恢复完整工作区必须保留versions内的大图文件；要重现原始调用与审阅，还须保留reports证据区、data来源快照及原清洗材料。凭据.local单独在本机保管，不进入版本包、代码提交或报告。

## 后续更新

1. 从CURRENT指定图谱读取，新的关系完善输出到独立运行目录。
2. 复用现有事实和证据；新记录待审，未定身份不自动晋升。
3. 通过结构、引用、来源与必要语义检查后，在v2分支下新增带日期/修订号的快照及manifest，保留前一快照。
4. 更新版本索引、CURRENT、变更记录和MASTER；保持使用者仍只面对v1历史分支与v2工作分支。
5. 提交相应代码/清单检查点。没有明确发布或推送指令时不远程推送。

目前尚未实现通用发布平台；已有`kg_versions.py init/check/current`用于本轮登记与完整性检查。后续登记新快照时应同步维护索引并执行检查，不能只手工替换CURRENT路径而漏掉清单。

## 本轮检查

5项治理测试通过；两个真实图谱复制前后哈希一致，数量与manifest一致，CURRENT及索引指向一致，路径不能逃出项目。没有重新抽取文献或调用模型。
