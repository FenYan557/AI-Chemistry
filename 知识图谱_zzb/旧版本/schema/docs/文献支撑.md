# 文献与标准支撑

> 设计背景材料，保留当时的论证；当前契约与实现状态以 [README](../README.md) 和 [schema.yaml](../schema.yaml) 为准。本文的性能估计、框架比较及文献检索结论未在本次整理中重新验证，不能作为当前实测结果。可比性键仅作初筛，关键口径缺失不能证明可比。

本文件把 `schema.yaml`、`constraints.yaml` 里的每一条关键设计，对应到公开标准或已发表工作，并标明**支撑强度**：

- **直接支撑**：有标准条文或论文明确采用同一做法；
- **间接支撑**：有同向工作，但具体形式由我们自己定；
- **工程判断**：找不到直接文献，属本项目的取舍，需靠本项目数据自证（见 [v1.0 历史评估](../../_archive/schema_v1.0_20261019/评估_可行性与性能.md)）。

查阅日期 2026-10-19。引用仅为定位用途，细节以原文为准。

## 一、逐条对应

### 1. 一个事实拆成"事件节点 + 限定条件"，而不是裸三元组

| 项目 | 内容 |
|---|---|
| 支撑 | W3C《Defining N-ary Relations on the Semantic Web》[1]；PROV-O[2]；DocEE 文档级事件抽取[10] |
| 强度 | 直接支撑（建模形状） |
| 具体做法 | 用 `Run`（条件组合）、`Observation`（测量）、`Claim`（结论）三类节点承载原本要写成一条边的多元事实；条件放在 `window` / `conditions` 里 |
| 我们多做的 | 把"条件"进一步分成 `reported / not_reported / unconstrained` 三态；标准与 PROV 都不涉及这一层 |

### 2. 结论必须带限定符（qualifier）与出处

| 项目 | 内容 |
|---|---|
| 支撑 | Wikidata statement model（statement = claim + qualifiers + references）[3]；Wikontic 的 ontology-aware 构图[5]；纳米出版物模型（assertion / provenance / publication info 三层）[8] |
| 强度 | 直接支撑 |
| 具体做法 | `Claim` 带 `window`（限定符），`EvidenceLink` 带 `anchors`（references）；两者分开存 |
| 我们多做的 | 出处精确到表格单元格 `(table_id,row,col)`，并要求 `quote` 字符级回读通过；Wikidata 的 references 只到来源级 |

### 3. 证据分级（T1–T4）

| 项目 | 内容 |
|---|---|
| 支撑 | GRADE 证据确定性分级框架[12]；ALCE 的可验证引用评测[11] |
| 强度 | 间接支撑（理念同向，级别定义不同） |
| 具体做法 | 四级：T1 有数有锚点且条件≥2 / T2 定性 / T3 推测或跨体系外推 / T4 二手转述 |
| 差异说明 | GRADE 面向临床证据体（研究设计、偏倚风险、不一致性），本项目的级别面向**单条文献事实的可核验性**。**不可声称"采用 GRADE"**，只能说"分级思路与 GRADE 一致" |

### 4. 谓词与指标取封闭枚举，不用自由文本

| 项目 | 内容 |
|---|---|
| 支撑 | Wikontic（以 Wikidata 的类/属性约束构图，强调高精度）[5]；Tab2Know（表格转 KB 需预定义框架）[6]；反向对照：AutoSchemaKG 主张从语料动态归纳模式[4] |
| 强度 | 直接支撑（封闭模式这一选择有先例） |
| 做法 | 16 个谓词带封闭 slot 签名；37 个指标分四族 |
| 与 AutoSchemaKG 的关系 | 方向相反：它以动态模式换覆盖面，我们以固定模式换一致性与可查询性。两者共同的判断是"模式必须显式存在"，这一点我们与它一致 |

### 5. 表格必须先有 ETL 画像才能抽数

| 项目 | 内容 |
|---|---|
| 支撑 | Tab2Know[6]；OmniDocBench（版面与表格解析评测，说明表格解析质量参差）[13] |
| 强度 | 间接支撑 |
| 做法 | 8 种 `etl_profile`，未定画像的表禁止产数值断言（C-TABLE-01）；OCR 不可读的表禁止产数值（C-TABLE-04） |
| 我们多做的 | 把"表格来源可信度"（`evidence` / `ocr_status`）作为一等字段并落到约束上 |

### 6. 单位、量纲与量的规范化

| 项目 | 内容 |
|---|---|
| 支撑 | OM（Ontology of units of Measure）[14]；QUDT[15]；ISO 80000 量与单位 |
| 强度 | 直接支撑 |
| 做法 | 单位 canonical 表 + 精确/需前提两档换算；数值必须带单位（C-UNIT-01）；电流密度必须声明波形（C-UNIT-03） |
| 我们多做的 | 换算"需前提"这一类（如面积基准不同）不与精确换算同级，面积基准进可比性键 |

### 7. 可比性：跨测量口径禁止比较

| 项目 | 内容 |
|---|---|
| 支撑 | JCGM 200:2012《国际计量学词汇》(VIM) 关于"计量学可比性"的定义——测量结果可比的前提是溯源到同一参考[16] |
| 强度 | 直接支撑（概念层面） |
| 做法 | `comparability_key = 指标|主方法|参比电极|孔型|AR桶|面积基准`；跨 key 禁止比大小、排序、判冲突（C-CMP-01） |
| 我们多做的 | VIM 给的是定义，没给工程实现。六段式编码、AR 分桶、`na` 与 `geometric` 不互比，都是本项目自定，属**工程判断** |

### 8. 窗口用区间表示，不退化成一个数

| 项目 | 内容 |
|---|---|
| 支撑 | Allen 区间代数（1983）[17] |
| 强度 | 间接支撑（我们只用区间包含/求交，没有用全 13 种关系） |
| 做法 | 连续量用 `kind: range` + `lo/hi`；扫轴在 Experiment 声明 `swept_params` |
| 我们多做的 | `not_reported` 不得参与求交当成满足（C-WIN-02） |

### 9. 化学身份不猜

| 项目 | 内容 |
|---|---|
| 支撑 | InChI / IUPAC 标识符标准[18]；ChEBI 本体；ChemDataExtractor 的"记录必须带单位与上下文才成立"原则[9] |
| 强度 | 直接支撑 |
| 做法 | 无外部来源不得填 SMILES/InChIKey（C-CHEM-01）；身份查不到时保留 `unresolved`，不猜 |
| 我们多做的 | 把"结构基元（Motif）"作为跨文献聚合层，基元 SMARTS 目前全部标草案，未验证不得对外使用 |

### 10. 约束必须可机器判定（而非写在文档里的口号）

| 项目 | 内容 |
|---|---|
| 支撑 | SHACL（W3C 推荐标准，图约束校验语言）[7] |
| 强度 | 直接支撑（理念与形态） |
| 做法 | 51 条约束中 48 条落到 Python 判定，分 reject/downgrade/warn 三档；3 条明确标注待实现 |
| 差异说明 | 我们没有用 RDF/SHACL 实现，用 JSON + Python。SHACL 支撑的是"约束应显式、可判定、可执行"这一方法论，不是具体语法 |

### 11. 材料领域的上位本体（说明不是凭空造）

| 项目 | 内容 |
|---|---|
| 支撑 | PMDco 3.0（Platform MaterialDigital 核心本体，Wiley ADV ENG MATER）[19]；MSEO（材料科学与工程本体，Computers in Industry）[20]；MatKG（自动生成的材料知识图谱，Scientific Data 2024）[21] |
| 强度 | 间接支撑 |
| 关系 | 这三者给出"材料领域需要区分样品/过程/测量/元数据"的共识；本项目在此之上补的是**工艺窗口**与**可比性**两件电镀特有的事，未直接复用其类层次（因为它们是 RDF/OWL 上位本体，粒度到"测量"为止） |

### 12. 评测口径

| 项目 | 内容 |
|---|---|
| 支撑 | DocEE 的 argument-level F1[10]；SciER 的科学文档实体/关系抽取基准[22]；ALCE 的引用可核验指标[11]；OmniDocBench 的解析覆盖评测[13] |
| 强度 | 直接支撑（评测方法） |
| 做法 | 报块覆盖率、锚定率、quote 三态、规则拦截分布；P/R 需人工金标按 argument 级别报 |
| 不做 | 不用 BLEU/ROUGE 评抽取（惩罚正确的重排），不用 TEDS 评表格结构（位图表无结构真值）——理由与 `01_补足原材料缺陷/out/report/信息保留度评估.md` 一致 |

## 二、没有直接文献支撑的部分（工程判断，共 7 处）

以下设计找不到对应标准或论文，属本项目取舍。**论文中应作为"我们的设计"提出，并给验证数据，不能说"依据某文献"**：

| # | 设计 | 为什么属于工程判断 | 验证路径 |
|---|---|---|---|
| 1 | `comparability_key` 的六段式与 AR 分桶 | VIM 只定义可比性概念，未给工程编码 | 已有实测定量（面积基准仅 23% 篇说明、表头 0/98 双条件）；需金标检验"跨口径误比"是否被拦住 |
| 2 | T1–T4 的判定阈值（条件参数 ≥2、明确措辞支） | GRADE 级别体系不面向单条事实 | 需 10 篇金标，报 tier 分布与人工复核一致率 |
| 3 | `support_class` 阈值（≥2 篇或 ≥3 独立 Run 记 consensus） | 无共识阈值文献 | 需检验 consensus 组与人工判断的一致性 |
| 4 | `presence` 三态 | 标准里只有"有值/无值" | 可用检索实验对比：把 not_reported 当满足 vs 显式缺失，看假支持率差异 |
| 5 | `block_id` 位置哈希 | 无标准做法（多为顺序号或随机 UUID） | 已有论证：清洗规则变动时顺序号会静默错位 |
| 6 | `defect_kind` 与 `etl_profile` 的枚举集合 | 领域自定义分类 | 需 98 张表逐张人工确认后检验覆盖率 |
| 7 | 三档处置（reject/downgrade/warn）的划界 | 无统一惯例 | 需报告各类占比与人工抽检误杀率 |

## 三、领域现状（可作为创新点，但表述要克制）

在公开文献与本体库中检索，未发现针对**电镀添加剂选型**的专用知识图谱或工艺窗口本体。最接近的是：

- 材料领域上位本体（PMDco、MSEO）——到"样品/过程/测量"粒度；
- 化学文献抽取工具与数据集（ChemDataExtractor、SciER、MatKG）——到"实体 + 关系"粒度；
- 通用 KG 构建方法（AutoSchemaKG、Wikontic、Tab2Know）——不涉及电镀工艺窗口与可比性。

因此可写：**"在上位模型与抽取方法上沿用已有标准与工作；工艺窗口三态、可比性键、证据分级阈值、位置哈希锚点为本项目提出"**。不可写：**"本 schema 遵循 PMDco / 依据 GRADE / 采用 SHACL 标准"**——那会被追问具体对齐到哪个类、哪个条款。
